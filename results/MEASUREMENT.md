# 측정 노트

이 폴더의 JSON 을 어떤 조건에서 어떻게 읽어야 하는지를 적는다.
GOAL.md §11(정직성 규칙)을 지키기 위한 문서다.

## 측정 환경

- 10코어 / 16GB / macOS. 신청 서버·PostgreSQL·Redis·부하 생성기가 **전부 한 머신**에서 돈다
- PostgreSQL 16 (Docker, `max_connections=200`), Redis 7 (Docker)
- 신청 서버는 Node 24 단일 프로세스, 커넥션 풀 기본 20
- **동시 커넥션 1만이 아니다.** "총 1만 요청 / 동시 N" 이다

## 파일 이름

```
M4-cap5000-c1000-x3-<timestamp>.json    내부 생성기, 정원 5000, 동시 1000, 3회 반복
k6-M4-cap5000-c1000-<timestamp>.json    k6, 같은 조건, 1회
```

## 두 시나리오를 나눈 이유

| | 정원 50 | 정원 5,000 |
|---|---|---|
| 1만 요청 중 | 99.5% 가 마감 판정 | 절반이 자리다툼 |
| 재는 것 | **마감 경로 비용** | **경합 자체** |
| 현실에 가까운 쪽 | 이쪽 | 인위적 조건 |

정원 50 만 재면 자리다툼을 거의 재지 않는다. M3(낙관적 락)가 정원 50 에서 RPS 1위인데
정원 5,000 에서 꼴찌가 되는 것이 그 증거다 — 마감 판정에 드는 왕복이 M3 는 1회뿐이기 때문이다.

## 내부 생성기와 k6 가 다르다

같은 조건(1만 요청 / 동시 1000)을 두 생성기로 던진 결과다.

### 정확성은 완전히 일치한다

M2·M3·M4·M5 는 두 생성기 모두에서 **초과 0 · 중복 0**, M1 은 두 생성기 모두에서 깨졌다.
**정합성 결론은 생성기와 무관하다.** 이 데모의 핵심 주장은 여기 있고, 그 부분은 흔들리지 않는다.

### 처리량은 다르다 — 그리고 규칙이 있다

RPS 비(내부 ÷ k6):

| | M1 | M2 | M3 | M4 | M5 |
|---|---:|---:|---:|---:|---:|
| 정원 50 | 1.9배 | **1.1배** | 2.1배 | 1.8배 | **3.4배** |
| 정원 5,000 | 1.3배 | **1.0배** | 1.1배 | 1.1배 | **2.6배** |

**서버가 느릴수록 두 생성기가 일치하고, 서버가 빠를수록 갈린다.**

- M2(비관적 락, 가장 느림)는 1.0~1.1배다. 서버가 확실한 병목이라 어느 생성기로 재도 같은 값이 나온다
- M5(Redis, 가장 빠름)는 2.6~3.4배다. 서버가 빨라서 **생성기 쪽이 병목**이 된다

즉 M5 의 내부 생성기 RPS 15,287 은 서버의 한계가 아니라 **측정 장비의 한계에 가깝다.**
이 수치를 "초당 1만 5천 건을 처리했다" 로 읽으면 과장이다.

### 왜 갈리는가

1. **k6 는 Docker 컨테이너 안에서 돈다.** `host.docker.internal` 을 거치는 네트워크 홉이 하나 더 있다
2. **내부 생성기는 Node 단일 스레드다.** 워커 1,000개를 만들어도 이벤트 루프 하나가 처리하므로
   실제 동시성이 1,000 에 못 미친다. k6 는 Go 기반이라 코어를 나눠 쓴다

2번의 증거가 M1 의 초과 건수다 — 같은 조건에서 내부 289건, **k6 693건**이다.
k6 가 더 촘촘한 동시성을 만들어 TOCTOU 구간에 더 많은 요청을 밀어 넣는다.
**깨지는 정도를 보여줄 때는 k6 수치가 더 정직하다.**

## 발표에 쓸 때의 규칙

- 정합성(초과·중복) 주장 → 두 생성기 어느 쪽을 써도 된다. 결론이 같다
- "얼마나 심하게 깨지는가" → **k6 수치**를 쓴다. 동시성이 더 진짜에 가깝다
- 처리량(RPS) 비교 → **상대 비교만** 한다. 절대값을 "이만큼 처리 가능" 으로 쓰지 않는다
- M5 의 우위 → Redis 는 인메모리이고 fsync 가 없다. 같은 조건의 비교가 아니라
  **"판정을 DB 밖으로 뺐을 때의 차이"** 로 설명한다

## 아직 확인하지 못한 것

- k6 는 시나리오당 1회만 돌렸다. 내부 생성기만 3회 반복해 중앙값을 냈다
- 두 생성기를 같은 머신에서 돌렸다. 부하 생성기를 다른 머신에 두면 수치가 또 달라진다
- M5 의 p99 는 정원 50 에서 566ms 로 M4(264ms)보다 **크다.** p50 은 19ms 로 훨씬 작은데 꼬리가 길다.
  요청이 짧은 시간에 몰려 순간 포화가 생기기 때문으로 보이나, 원인을 끝까지 확인하지 않았다
